# B1 · N0 结果：NeoForge 引导链的类图谱已可导出

> 日期：2026-11-15
> 线：B1（NeoForge / Minecraft 1.21.1 / iOS 无 JIT）
> 作业：CircleCI `neoforge-n0` #134（macOS arm64，11:30:32→11:31:23 UTC）

## 1. 做了什么

在 macOS 构建机上用 Java 启动 **NeoForge 21.1.250 服务端**（headless），
通过 `JAVA_TOOL_OPTIONS` 挂一个 javaagent，把**每个被加载的类在全部转换之后**的字节落盘：

```
JAVA_TOOL_OPTIONS=-javaagent:dumpagent.jar=<dir> -Dmixin.debug.export=true
```

选服务端的理由：它是 headless 的，正好验证「引导链 → Mixin → AT → 类加载」全流程，
不需要窗口；客户端类留给 N1。

## 3. 阶段性结论

1. **NeoForge 21.1.250 + 1.21.1 的引导链可以在无窗口环境跑通**，启动 3.6 秒。
2. **转换后的类字节可以被完整捕获**——这是「构建期静态化」的前提，N0 第一半通过。
3. 仍然存在的老问题没变：`modlauncher`（20 个类引用 `ModuleLayer`）与
   `securejarhandler`（`defineClass`/`Unsafe`）在运行期构建模块图。
   我们的路线是**在构建期跑完它们**，只把产物（这份 class 图谱）带进 AOT；
   运行期不再启动 ModLauncher。

## 4. 下一步（N0.5，决定性的那一半）

把这份 11,962 个类的图谱**脱离 ModLauncher**做一次 GraalVM `native-image` 冒烟：

- 输入：dump 的类树 + 服务端入口的最小 launcher
- 目标：macOS arm64 可执行文件（先不做 iOS，先验证封闭世界分析能否通过）
- 通过标准：链接成功、启动后打印服务端版本并正常退出
- 失败即暴露必须重写的运行期组件（反射注册、模块层、动态代理）

只有 N0.5 通过，才值得投入 N1（iOS 真机启动）。

## 4b. N0.5 实测结果（2026-11-15 晚）

| 检查 | 结果 |
|---|---|
| GraalVM native-image 能否消费这份图谱 | **能**：`Finished generating 'n0smoke' in 15.8s`，产出 13 MB 可执行文件 |
| 可执行文件能否运行 | **能**：打印 `SharedConstants / Level / Item / Connection / NeoForge / ModLoader / Mixin` 后输出 `ok` |
| 图谱是否完整 | **不完整**：纯 JVM 冒烟只过 7/10 关键类 |

缺失类的根因（三轮排除后确定）：

1. dump 只包含“运行期被加载过”的类；
2. 用服务端 classpath 的 jar 补不齐——jar 里的条目名是 SRG/混淆名，运行期类名是官方名；
3. 按 jar 条目名强制 `Class.forName` 只成功 220 / 26,067；
4. `ModuleLayer` 不可用——游戏类在**未命名模块**里（`getLayer()` 为 null，0/0）；
5. 用 agent 线程的 context loader 找不到 `net.minecraft.SharedConstants`（拿到的是 bootstrap/app loader，`runtime roots: 0`）。

结论：**AOT 工具链这一侧已经验证通过**（能编译、能产出可运行镜像）；
剩下的唯一问题是“如何在构建期拿到完整的运行期类集合”，这需要
从 FML 实际使用的类加载器/模块位置取类（而不是从 jar 枚举），或者直接改造成
构建期 transformer 管线。这一步决定 B1 后续的架构。
