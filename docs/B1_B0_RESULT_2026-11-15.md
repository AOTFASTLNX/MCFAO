# B1 线 · B0 结果：完整类图谱已拿到（2026-11-15 夜）

> 对应计划：`docs/B1_BUILD_TIME_PIPELINE_PLAN_2026-11-15.md`
> 作业：CircleCI `neoforge-n05` **#162（success）**，macOS arm64

## 1. 关键突破

前几轮失败的根因是**拿不到锚点**：agent 线程的 context loader 看不到游戏类，
`ModuleLayer` 又在未命名模块上返回 null。这一轮改成用
`Instrumentation.getAllLoadedClasses()` 找一个已加载的 `net.minecraft.*`，结果：

```
anchor=net.minecraft.SharedConstants
loader=cpw.mods.modlauncher.TransformingClassLoader
module=minecraft layer=present
runtime roots: 2
```

由此拿到 FML 真正使用的两个模块 jar：

| 模块 jar | 强制定义成功 | 失败 |
|---|---|---|
| `server-1.21.1-20240808.144430-srg.jar` | 6,148 | 0 |
| `neoforge-21.1.250-universal.jar` | 1,414 | 78（`RuntimeDistCleaner` 拒绝的服务端不存在的客户端类，符合预期） |

再加上从运行期 classpath 的库 jar 逐类定义（改用游戏 loader 而不是系统 loader）：

```
forced roots ok=7562 fail=78; jars ok=25983 fail=66
```

**合计约 33,500 个类被强制走完转换并落盘**。

## 3. 结论

**B0 的核心问题（构建期拿全运行期类集合）已经解决**：锚点从 Instrumentation 拿、
模块 jar 从 loader 的模块表拿、库从运行期 classpath 拿，三条腿都在构建期完成，
不依赖运行期 ModLauncher。
